# Scheduled agent tasks

Scheduled opens from the sidebar directly below Library. Users can create daily,
weekday, weekly, monthly, custom cron, one-time, or relative-delay tasks. Each run
creates its own chat in the selected project. Run history links to those chats.

The agent has `create_scheduled_task`, `list_scheduled_tasks`,
`update_scheduled_task`, and `delete_scheduled_task` in every durable chat,
including chats generated by another schedule. Creation instructions must be
self-contained because a run starts a new conversation. Conversational creation
inherits the source chat's model; creation in the UI uses organization defaults.
Every admission resolves current model permissions, connectors, memory, and
allowance through the ordinary agent admission path.

## Reference and deliberate differences

The starting reference was [ZCode](https://github.com/zai-org/ZCode), inspected
from a shallow clone. Its [scheduler](https://github.com/zai-org/ZCode/blob/main/packages/desktop/src/scheduler/index.ts)
uses a persistent polling process, transactional claims, a run ledger, crash
recovery, and separate manual triggers. Its calendar helper uses Croner. Berry
uses the same calendar library (pinned to 10.0.1) and those scheduling patterns,
with an implementation adapted to the enterprise web platform.

| Area | Berry behavior |
| --- | --- |
| Ownership | Owner-scoped API and tools; forced tenant RLS on schedules, runs and operation receipts. |
| Multiple replicas | PostgreSQL row locks, occurrence uniqueness, fenced dispatch leases and ordinary turn idempotency. |
| Clock time | Explicit IANA timezone, DST-aware cron; relative delays use the database clock. |
| Downtime | Coalesce missed recurring occurrences into one overdue run, then advance from now. ZCode skips occurrences outside its grace window. |
| Overlap | Skip a recurring occurrence when the preceding chat still has pending or active work. Manual starts reject an existing active run. |
| Restart | Recover an admitted durable turn from its stable request ID before retrying. A lost admission response cannot mark that chat failed. |
| Editing | Name-only edits keep paused/completed state and the original occurrence time. Pausing, deleting or rescheduling cancels pending dispatches. Already dispatching chats can finish. |
| History | Separate schedule state from the actual durable turn state; preserve generated chats when deleting a schedule. |
| Conversation tools | Available in any task, rather than limiting schedule creation to a special source task. |

## Execution and operations

Migration 71 adds `scheduled_tasks`, `scheduled_task_runs`, and
`scheduled_task_operations` in one transaction. It changes no existing task or
message data. Schedules require `BERRY_DURABLE_RUNNER_ENABLED=true` and
PostgreSQL. No additional scheduler service or broker is required.

The API polls every ten seconds, creates up to twenty due occurrences per poll,
then claims up to ten pending dispatches. A claim has a five-minute durable lease.
Transient admission failures retry after thirty seconds, up to three attempts.
Permanent policy/validation failures remain visible in history. Agent execution
continues through the normal durable worker and outbox. This is minute-granularity
scheduling, not a guarantee of execution at the exact second of a cron boundary.

The API endpoints are under `/v1/scheduled-tasks`: list/create, update/delete by
ID, `/runs` for history, and `/run` for an idempotent manual start. Create, update,
and run requests can carry stable operation IDs; tool calls use their durable step
ID. A user can retain up to 100 schedules.

Deploy the API, both worker roles, and web together using the service deployment
path. Run migrations and refresh the existing API/worker database grants before
starting the new scheduler. The worker Docker build now includes `packages/db`.
Keep `deploy/.env.production` unchanged. Existing production source hotfixes must
be retained when assembling a release.

## Verification

Run the focused web/API/worker checks from AGENTS.md. Calendar and form tests cover
timezone conversion, DST, invalid local times, relative delays and cron presets.
Dispatcher tests cover normal admission, revoked membership, retries, safe errors,
overlapping polls and shutdown. Client tests cover stable manual operation keys
and support-view restrictions.

`scripts/test-scheduled-tasks.mjs` requires a migrated disposable loopback
PostgreSQL database. It exercises replica claims, downtime, one-time work, worker
completion and projection, restart recovery, stale leases, editing/deletion,
transient failures, membership revocation, spend limits, chat tools, ownership and
restricted-role RLS. `--serve` exposes a loopback-only browser fixture; it does not
contact live models or use production credentials.
